# 簡易シフト管理システム デモ 実装計画

## 背景と目的を定める

現行リポジトリは、Vite の `vanilla-ts` scaffold と Vitest・oxlint・oxfmt だけを持つ最小構成である。これを、Cloudflare Workers + D1 をサーバ・保存基盤とする SvelteKit アプリへ置き換え、管理者が店舗・飲食スタッフの1日シフトを入力・求解・確認できるデモにする。

この計画は実装を行うための順序と検収条件を定めるものであり、各ステップを原則として1つのPRに収まる粒度に分ける。各PRの検証が通ってから次のステップへ進む。

現状の品質検査は、`CLAUDE.md` に記載された次の6項目を基準にする。

1. テスト実行
2. 型検査
3. lint
4. format
5. カバレッジ出力
6. CI

カバレッジ閾値90は要求水準ではなく保持線なので維持する。Vitest 4では `coverage.all` が廃止されているため、coverageスクリプトの `--coverage.include=src/**` 相当の指定を残す。これを外すと、テストからimportされていないファイルが分母に入らず、未テストのファイル追加で閾値が形骸化する。

## 順序と依存関係を定める

1. 現行のVite構成を先にSvelteKitへ置き換えないと、以降の `+server.ts`、D1バインディング、Svelteコンポーネントの配置を確定できない。
2. scaffold置き換えの直後にHiGHSのWorker実行を最小検証する。WASMのバンドル、初期化、gzip後サイズ、CPU時間のいずれかが成立しなければ、D1や画面を作り込む前に `yalps` へ切り替える必要があるためである。
3. 新しい構成ができた後に `CLAUDE.md` を更新し、以降の実装者が古い目的・ディレクトリ・検査方法を参照しないようにする。
4. D1の論理データ単位を先に確定し、そのデータを入力としてモデルを作る。モデルはソルバー呼び出しから分離して先に単体検証する。
5. モデルを呼び出すAPIを作ってから、APIを利用する画面を作る。初期データはAPIと画面の契約が定まった後に投入し、最後にWranglerでデプロイ手順を検証する。

## 各ステップの作業と検収を定める

### ステップ1: scaffoldをSvelteKitへ置き換え、品質検査を組み直す

**対象ファイル**

- `package.json`、`package-lock.json`
- SvelteKit設定、Vite設定、TypeScript設定、Vitest設定など、scaffold差し替えで必要になる設定ファイル
- `src/` 配下のエントリとテストの足場
- `.github/workflows/quality.yml`
- 置き換え対象となる現行の `index.html` などのVite scaffoldファイル

**作業内容**

- Vite `vanilla-ts` を SvelteKit + `@sveltejs/adapter-cloudflare` に置き換える。
- Workerで動くビルド・ローカル開発の骨格を作り、以降のAPIと画面の配置先を確定する。
- `npm test`、`npm run typecheck`、`npm run lint`、`npm run format:check`、`npm run coverage` がSvelteKit構成で動くようにスクリプトとCIを組み直す。coverageのJSON出力先と6項目のCI実行も維持する。
- coverageの4指標の閾値90を保持し、`--coverage.include=src/**` 相当の指定を残す。
- SvelteコンポーネントのテストでDOMが必要かをこのステップで決定する。jsdom等を採用する場合は依存とVitest設定までこのPRに含め、採用しない場合はDOMを使わないテスト境界と理由を設定・文書に残す。具体的な環境は未決である。

**完了条件**

- SvelteKitの最小ページがビルドでき、adapter-cloudflareを使う構成が成立している。
- 6項目の検査がSvelteKit構成で実行でき、coverageの出力と閾値90が有効である。
- DOMテスト環境を採用するかどうかが決まり、採用時はSvelteコンポーネントの最小テストが実行できる。

**検証手段**

- 依存を導入した実装環境で `npm run build` を実行する。
- `npm test`、`npm run typecheck`、`npm run lint`、`npm run format:check`、`npm run coverage` を実行し、`coverage/coverage-final.json` の生成と閾値判定を確認する。
- GitHub Actions相当のCIをPRで実行し、6項目が非破壊コマンドだけで通ることを確認する。
- `npm run dev` で最小ページを開き、SvelteKitのルートが表示されることを手動確認する。

### ステップ2: HiGHSをWorkerで最小検証する

**対象ファイル**

- 検証用の `+server.ts` とダミーMILP生成コード（実際の配置はステップ1で確定したSvelteKit構成に合わせる）
- `.wasm` のimportとHiGHS loader初期化に関する検証コード
- Workerビルドとローカル実行に必要な設定ファイル
- 検証結果を記録するドキュメントまたはPR本文

**作業内容**

- 本件の定式化をダミーデータで生成し、約3,000個の0-1変数を含むMILPを用意する。
- `wrangler dev` 上の `+server.ts` からそのMILPを解き、解が返る最小経路を作る。
- Cloudflareが公式に示すES module形式のWASM読込を前提に、`highs` loaderへ `wasmModule` を渡す経路を検証する。HiGHSの正確なloader APIや型は、導入したパッケージの実体で確認してから固定する。
- adapter-cloudflareのビルドで `.wasm` がバンドルされるか、gzip後のバンドルサイズ、WorkerのCPU時間を測定する。
- 次の4点を検証結果に明記する。
  1. adapter-cloudflareのビルドで `.wasm` がバンドルされるか。
  2. gzip後のサイズが、公式Limitsページで確認した上限内か。
  3. `wasmModule` 経由でloaderを初期化できるか。
  4. 求解のCPU時間が、採用予定のPaidプランの上限内か。
- 調査時の参考値として、`highs@1.14.2` の `build/highs.wasm` は3,078,627バイト、`build/highs.js` は68,966バイトだった。ただし非圧縮値であり、gzip後はこの検証で測る。値の出典は[jsDelivrのパッケージAPI](https://data.jsdelivr.com/v1/package/npm/highs@1.14.2)である。
- Workersのサイズ・CPU・メモリ制限は、コミュニティ情報を採用根拠にせず、[公式Limitsページ](https://developers.cloudflare.com/workers/platform/limits/)で再確認する。Free/Paidのどちらを採用するかはこの結果を材料にユーザーが判断する未決事項とする。
- HiGHSがWorkerで動かない、サイズが上限を超える、またはCPU時間が成立しない場合は、退避先の `yalps` へ切り替え、同じ規模・同じ検証項目で再検証する。

**完了条件**

- `wrangler dev` 上の `+server.ts` が約3,000変数規模のMILPを解き、解を返す。
- 上記(a)〜(d)の結果、使用プラン、実測したCPU時間、gzip後サイズがPRに記録されている。
- HiGHSが不成立の場合は `yalps` で同じ検証を完了し、採用ソルバーが決まっている。未解決の場合は画面・D1へ進めず、ユーザー判断待ちとして残す。

**検証手段**

- `npm run build` で本番相当バンドルを作る。
- `wrangler dev` を起動し、検証用 `+server.ts` をHTTP操作して解の返却を確認する。
- 出力されたWorker資産に `.wasm` が含まれることを確認し、gzipした成果物のバイト数を記録する。
- ローカル実行の計測値と、公式Limitsページで確認した上限を比較する。
- 失敗時はsolverだけを `yalps` に差し替え、同じ `npm run build`・`wrangler dev`・サイズ計測・CPU計測を再実行する。

**根拠と要確認事項**

CloudflareのWASM読込手順、adapter-cloudflareでのバンドル方法、HiGHS loaderの `wasmModule` 経路、gzip後サイズ、現行のWorker制限値は依頼文だけでは動作確認できていない。ここをD1やUIより先に検証する。

### ステップ4: D1スキーマとマイグレーションを作る

**対象ファイル**

- D1のマイグレーションSQL（`migrations/` 配下）
- WranglerのD1バインディング設定
- D1アクセスを担当するサーバ側モジュールと型
- スキーマ・リポジトリの単体テストまたは統合テスト

**作業内容**

- 日付をまたいで共有する従業員データ（名前、役割集合、勤務長さ上下限）を保存できるスキーマを作る。
- 日付に属する必要人数（コマ×役割）、従業員ごとの当日の出勤可能時間帯、固定割当と求解結果を保存できるスキーマを作る。
- 1日1枚という論理単位を、日付をキーに読み書きできるようにする。新しい日付の作成時はテンプレートを作らず空データにする。
- 初期化処理が全データを初期状態へ戻せるよう、初期化対象と初期データ投入方法を定める。
- テーブル分割・JSON保存・インデックスなどの物理設計は、日付単位と共有範囲を壊さないように決める。SQLの型、制約、D1の制限値は実装時に公式資料と実行環境で確認する。

**完了条件**

- マイグレーションを適用すると、共有従業員データと日付データを独立して保存・取得できる。
- ある日付の変更が別の日付の必要人数・出勤可能時間帯・結果を変更しない。
- 新しい日付が空で作成され、リセット対象に全データが含まれる。

**検証手段**

- プロジェクトで確定したWranglerのD1ローカル適用コマンドを実行し、マイグレーションを適用する。コマンド構文はWranglerのバージョンに合わせて要確認とする。
- 共有従業員1件と異なる2日分の入力を作成し、読み書きの往復をテストする。
- 新しい日付を作ってテンプレートがないこと、初期化後に初期状態へ戻ることをD1ローカル環境で確認する。
- `npm test` と `npm run typecheck` を実行する。

### ステップ5: 最適化モデルを実装する

**対象ファイル**

- ドメイン型・勤務パターン生成のモジュール（`src/lib/` 配下）
- LPテキストの生成を担当する純関数
- LP解をドメインの割当結果へ変換する純関数
- ソルバーを初期化・呼び出しするWorker側モジュール
- モデル生成・解釈の単体テスト（`src/` 配下の `*.test.ts`）

**作業内容**

- 従業員、役割、日付入力から、実行可能な `(e, r, p)` 候補と不足変数を作る。
- 1日1勤務以下、勤務長さ上下限、営業時間、出勤可能時間帯、担当可能役割、コマ×役割の不足制約、ピン留め固定をLPテキストに反映する。
- `M·Σu + ΣLx` の目的関数を生成し、`M` は実装時に決めた根拠とともに定数化する。
- LPテキストの生成と、ソルバー出力の解釈を、ソルバーを呼び出さない純関数として分離する。
- ソルバー実行（WASMの初期化、求解、エラー処理）を別モジュールに置く。HiGHSを採用できなかった場合はステップ2の `yalps` 検証結果に合わせて実行部分だけを切り替える。
- HiGHSの入力・解出力の具体的なAPIは、ステップ2と導入パッケージの実体で確認してから実装する。依頼文にないAPI仕様を仮定しない。

**完了条件**

- 純関数だけで、既知の入力から期待する変数・制約・目的関数を含むLPテキストを生成できる。
- 純関数だけで、ソルバー出力から通常割当、不足、固定割当を復元できる。
- 1日1勤務以下、役割、可能時間帯、勤務長さ、日次必要人数、ピン留めの各確定規則をテストで検証している。
- 実行モジュールを通じて、ステップ2で成立したソルバーから解を取得できる。

**検証手段**

- まずモデル生成・解釈のテストを追加し、`npm test` で実行する。
- 変数と制約の件数、係数、固定条件、不足が必要人数を補うこと、総勤務時間の計算をテストする。
- `npm run typecheck` と `npm run coverage` を実行し、純関数をcoverage対象に含める。
- ダミー入力と小さい実データをソルバーへ渡し、期待する不足最小化・勤務時間最小化の結果を確認する。

### ステップ6: `+server.ts` APIを実装する

**対象ファイル**

- 従業員リソースの `+server.ts`
- 日付リソースの `+server.ts`
- 求解用の `+server.ts`
- 初期化用の `+server.ts`
- D1リポジトリ、入力検証、APIのリクエスト・レスポンス型
- APIテスト

**作業内容**

- 従業員のCRUDを提供する。
- 日付ごとの必要人数、出勤可能時間帯、固定割当、求解結果を読み書きする。
- 求解要求で日付の入力と固定割当をモデルへ渡し、固定割当を保った残りの解を返す。
- 保存する結果を「固定した割当 + ソルバー出力」とする。再求解で固定割当が消えたり、別の割当として上書きされたりしないようにする。
- 全データを初期状態へ戻すAPIを提供する。
- APIの具体的なルート、HTTPメソッド、JSON形式はこのステップで定め、要件書の責務とD1の論理単位に対応させる。認証・認可は追加しない。
- 画面から入力変更時と再求解時に自動保存できる書き込み境界を用意する。保存ボタンやundo用のAPIは作らない。

**完了条件**

- 管理者が必要とする従業員CRUD、日付データの読み書き、求解、初期化が `+server.ts` 経由で一通り動く。
- ピン留めを含む求解結果を保存して読み戻せる。
- APIの入出力とD1の保存範囲がテストで固定されている。

**検証手段**

- `wrangler dev` を起動し、HTTPクライアントまたはブラウザの開発者ツールから各APIを操作する。
- 従業員を作成し、2日分の入力を保存・取得し、片方だけを再求解して結果を確認する。
- 固定割当を含む求解を行い、再取得した結果に固定割当とソルバー出力の両方があることを確認する。
- 初期化APIを実行し、全データが初期状態に戻ることを確認する。
- `npm test`、`npm run typecheck`、`npm run coverage` を実行する。

### ステップ7: 管理者画面を実装する

**対象ファイル**

- SvelteKitのページ・レイアウト
- 従業員管理コンポーネント
- 日付選択・必要人数入力コンポーネント
- 出勤可能時間帯入力コンポーネント
- シフト表、結果、不足人数、ピン留め操作のコンポーネント
- 初期化操作と自動保存のクライアント処理
- Svelteコンポーネントテスト

**作業内容**

- 従業員管理、日付選択、コマ×役割の必要人数表、従業員ごとの出勤可能時間帯入力を作る。
- 求解結果をシフト表として表示し、不足人数をコマ×役割で確認できるようにする。
- 管理者が結果をピン留めし、従業員・開始・長さ・役割を固定して再求解できる操作を、試作で決めたUIとして実装する。具体的な操作方法は要件では未決である。
- 入力変更時と再求解時にAPIへ自動保存し、保存ボタンを表示しない。undoも表示しない。
- 「初期データに戻す」を実装する。認証なしの前提を画面の権限モデルに追加しない。
- 新しい日付が空から始まること、設定画面・印刷・CSV・確定状態がないことを画面構成に反映する。

**完了条件**

- 管理者が、従業員登録から日付入力、求解、結果・不足確認、ピン留め再求解、初期化まで画面だけで操作できる。
- 入力変更と再求解のたびに保存され、画面再読み込み後も日付単位のデータと結果を取得できる。
- 役割を複数持つ従業員と、出勤可能時間帯未入力の従業員を画面で扱える。

**検証手段**

- `npm run dev` または `wrangler dev` で画面を開き、管理者操作を手動で一巡する。
- 必要人数、出勤可能時間帯、従業員属性を変更してから再読み込みし、自動保存を確認する。
- 結果をピン留めして再求解し、固定した割当が維持され、不足表示と残りの割当が更新されることを確認する。
- 新しい日付を選んだとき空であること、初期化操作後にデモ初期状態へ戻ることを確認する。
- Svelteコンポーネントテストを `npm test` で実行し、`npm run typecheck`、`npm run lint`、`npm run format:check` も実行する。

### ステップ8: デモ用初期データを投入する

**対象ファイル**

- 初期データの定義またはseed処理
- D1マイグレーションまたは初期化処理が参照するフィクスチャ
- 初期データのテスト

**作業内容**

- デモ用の従業員と、数日分の必要人数・出勤可能時間帯を用意する。
- 従業員は名前、複数の担当可能役割、勤務長さの上下限を持てるようにする。
- 日付ごとに異なる必要人数・出勤可能時間帯を持たせ、日付データが従業員の共有属性と混ざらないことを示す。
- 初期化APIが同じ初期データを再現できるよう、投入元を一箇所に定める。
- 従業員数は10人程度を目安にするが、上限として実装しない。具体的な名前・日付・人数は実装時に決める。

**完了条件**

- 初回起動または初期化後に、デモの流れを試せる従業員と複数日分の入力が存在する。
- 初期化を何度実行しても同じ初期状態へ戻る。
- 初期データにない新しい日付は空で始まる。

**検証手段**

- D1ローカル環境を初期化し、画面またはAPIで初期従業員・日付・入力を確認する。
- 一部を編集してから初期化APIを実行し、従業員・日付入力・結果が初期値へ戻ることを確認する。
- 初期データを読み込んだ状態で `npm test` と `npm run typecheck` を実行する。

### ステップ9: WranglerとD1のデプロイ手順を整える

**対象ファイル**

- Wrangler設定ファイル（ファイル形式・パスは実装時に確定）
- D1の作成・バインディング・マイグレーション手順を記載するプロジェクトドキュメント
- 必要なデプロイ用npmスクリプト
- CIまたはデプロイ前検証に必要な設定

**作業内容**

- `wrangler` でWorkerをビルド・ローカル実行・デプロイする手順を定める。
- D1を作成し、Workerから参照するバインディング名を設定し、マイグレーションを適用する手順を定める。
- SvelteKit + adapter-cloudflare の成果物にWASMまたは退避ソルバーが正しく含まれることをデプロイ前に確認する。
- Free/Paidプランの選択、公式Limitsで確認したサイズ・CPU制限、ステップ2の実測値をデプロイ条件に記録する。Free/Paidは要件上未決なので、ユーザー判断なしに固定しない。
- デプロイ後の読み書き、求解、ピン留め、初期化のスモークテストを手順化する。認証がないため、誰でも読み書きできる前提も明記する。
- Wranglerのバージョンに対応するD1作成・バインディング・マイグレーションコマンド、adapterの設定細部、D1制限値は公式資料と対象環境で確認してから確定する。

**完了条件**

- 新しい環境で、D1作成、バインディング、マイグレーション、Workerデプロイを再現できる。
- デプロイ後に画面、API、D1保存、求解、初期化の一連の機能が動く。
- デプロイ成果物のgzip後サイズと求解CPU時間が、採用プランの公式制限内であることを記録している。

**検証手段**

- 対象Wranglerバージョンで、D1作成・マイグレーション・ローカル実行・デプロイのコマンドを実行する。正確なコマンド構文はそのバージョンの公式ドキュメントで要確認とする。
- デプロイ後のURLで、従業員CRUD、日付入力、自動保存、求解、ピン留め再求解、初期化を手動確認する。
- `npm run build`、`npm run lint`、`npm run format:check`、`npm run typecheck`、`npm run coverage` をデプロイ前に実行する。
- [Cloudflare Workersの公式Limitsページ](https://developers.cloudflare.com/workers/platform/limits/)と実測結果を照合し、WASMを含むgzip後サイズとCPU時間を記録する。
