# 簡易シフト管理システム デモ 要件書

この文書は、数理最適化ソルバーを裏方に使う、店舗・飲食スタッフ向けの簡易シフト管理システムの初期版を定める。ここでいう「初期状態」は、デモ用の初期データを投入した状態を指す。

## このデモが示す対象と利用者を定める

- デモの目的は、ソルバーの機能を見せることではなく、シフト管理システムとして使えることを見せることである。ソルバーは裏方として扱い、人手で作ったシフトとの比較機能は持たない。
- 対象業務は、店舗・飲食のスタッフシフトである。
- 利用者は管理者だけである。従業員はシステムを操作せず、従業員の希望や出勤可能時間帯は管理者が代理入力する。
- 認証は行わず、誰でも読み書きできる前提とする。

根拠: 決定事項 #1〜#3、#12。

## 管理者が行える操作を定める

管理者は、次の情報を入力・変更・閲覧できる。

- 従業員の追加・編集・削除。従業員ごとに、名前、できる役割の集合、勤務長さの下限・上限を管理する。
- 対象日付の選択。新しい日付はテンプレートをコピーせず、空の状態から始める。
- 対象日付の必要人数の入力。必要人数は、時間帯コマと役割の組み合わせごとに入力する。
- 対象日付における各従業員の出勤可能時間帯の入力。入力できる区間は1区間とし、未入力はその日の休みとして扱う。
- 求解の実行と、割当結果およびコマ・役割ごとの不足人数の閲覧。
- 結果の一部をピン留めして再求解する操作。管理者が固定した「従業員・開始・長さ・役割」の組を固定条件として渡し、残りをソルバーで埋め直す。
- すべてのデータを初期状態へ戻す「初期データに戻す」操作。従業員、日付ごとの入力、固定割当、求解結果を含む全データを初期状態に戻す。

保存は自動で行う。入力が変更されたとき、および再求解したときにサーバへ保存し、保存ボタンは設けない。undo 機能も持たない。

根拠: 決定事項 #9、#12、#13、#17。操作 UI の具体的な配置やピン留め方法は未決であり、実装時に試作して決める。

## 画面や操作がなくても成立する業務規則を定める

- 計画期間は1日分である。日をまたぐ連勤上限、週の勤務時間の均し、その他の日をまたぐ制約は扱わない。
- 割当の単位は30分刻みの時間帯コマである。
- 1人が1日に持てる勤務は、連続した1勤務以下である。勤務を持たない従業員も許容する。
- 1勤務に休憩は含めない。休憩はモデルの対象外である。
- 従業員は複数の役割を担当できる。各勤務で実際にどの役割に入るかはソルバーが決める。
- 従業員の出勤可能時間帯は当日について1区間だけ持つ。未入力の場合、その従業員には当日の勤務可能なパターンがない。
- 従業員は時給を持たない。勤務時間の合計を、初期版における勤務量の指標とする。
- 必要人数はコマと役割ごとに定義する。不足は許容するが、不足人数に罰則を課して最小化する。
- 過剰配置には直接の罰則を課さない。勤務時間の最小化によって、必要以上の勤務を間接的に抑える。
- ピン留めされた割当は、求解結果の一部ではなく、ソルバーに渡す固定条件である。保存する結果は、固定した割当とソルバー出力を合わせたものである。

根拠: 決定事項 #4、#5、#7、#8、#9、および初期版の既定値。

## 日付と従業員のデータ所有範囲を定める

日付ごとに1枚のシフト計画を持つ。データの所有範囲は次のとおりとする。

| データ             | 所有範囲           | 内容                                       |
| ------------------ | ------------------ | ------------------------------------------ |
| 従業員             | 日付をまたいで共有 | 名前、できる役割の集合、勤務長さの上下限   |
| 出勤可能時間帯     | 日付に属する       | 従業員ごとの当日の1区間。未入力は休み      |
| 必要人数           | 日付に属する       | コマ × 役割ごとの必要人数                  |
| 固定割当と求解結果 | 日付に属する       | ピン留めした割当とソルバー出力の組み合わせ |

新しい日付にはテンプレートを適用しない。初期状態へ戻す操作だけは、デモ用の初期データを持つ状態へ全体を戻す。

根拠: 決定事項 #13、#12。

## 最適化モデルの変数と制約を定める

### パターンを定める

- 勤務パターン `p` は、開始コマ `s` と長さ `L` の組である。
- `L` は従業員 `e` ごとの勤務長さの下限・上限の範囲から選ぶ。
- `s + L` が営業時間内に収まり、かつ勤務区間 `[s, s + L)` が従業員 `e` の当日の出勤可能時間帯に含まれるパターンだけを候補にする。
- 従業員が担当できる役割 `r` との組み合わせごとに、勤務パターンの候補を作る。出勤可能時間帯が未入力の場合は候補を作らない。

### 変数を定める

- `x[e][r][p]` は、従業員 `e` を役割 `r` の勤務パターン `p` に割り当てるかを表す0-1変数である。
- コマ `t` と役割 `r` ごとに、不足人数を表す `u[t][r] >= 0` を置く。

### 制約を定める

- 各従業員は1日1勤務以下とする。

  `Σ_r Σ_p x[e][r][p] <= 1`

- 各コマ・役割の実割当と不足人数の合計が、必要人数以上になるようにする。

  `Σ_{e,p: p が t を含む} x[e][r][p] + u[t][r] >= 必要人数[t][r]`

- ピン留めされた `(e, r, p)` については、`x[e][r][p] = 1` とする。

### 目的関数を定める

次を最小化する。

`M · Σ u[t][r] + Σ L(p) · x[e][r][p]`

- 第1目的は不足人数の合計を減らすことである。
- 第2目的は総勤務時間を減らすことである。
- `M` は、不足1単位の改善が総勤務時間の増分より常に優先される十分大きな値とする。具体的な値は実装時に決める。

### 規模の目安を定める

営業時間14時間、30分コマ、勤務長さ4〜8時間の場合、1人・1役割あたり約150パターン、10人・2役割で約3,000個の0-1変数を目安とする。この人数は規模見積りであり、上限制約ではない。

根拠: 依頼で確定した「最適化モデルの定式化」と「規模の目安」。営業時間、役割名、`M` の具体値は未決である。

## ソルバーと実行基盤を定める

- サーバは Cloudflare Workers とし、保存には D1 を使う。サーバが保存と求解を担う。
- Web アプリは SvelteKit と `@sveltejs/adapter-cloudflare` で構成する。現行の Vite `vanilla-ts` scaffold は置き換える。
- API は SvelteKit の `+server.ts` で実装し、D1 はプラットフォームバインディング経由で扱う。
- 主ソルバーは npm `highs` のHiGHS WASMビルド（1.14.x、LGPL）とする。入力形式は LP/MPS テキストとする。Worker 上で実行する。
- `highs` を Worker で動かせない場合の退避先は `yalps`（pure TypeScript、MIT）とする。退避時もWorker上で動作することを検証する。
- `glpk.js` は GPL-3.0 のため配布物への伝播を理由に採用候補から除外する。`javascript-lp-solver` は候補として調査されたが、主ソルバーには選ばない。OR-Tools CP-SAT の公式 WASM ビルドは無い。
- 認証・認可の仕組みは置かないため、公開環境でも誰でも読み書きできる前提を引き継ぐ。

根拠: 決定事項 #10〜#12、#16。候補のライセンス・実装形態・ベンチマーク情報は、依頼に記載された調査結果による。

## 初期版の既定値を定める

| 項目           | 初期版の既定値 | 注記                                                                                                      |
| -------------- | -------------- | --------------------------------------------------------------------------------------------------------- |
| 過剰配置       | 罰則なし       | 人件費を総勤務時間として、目的関数の第2項で間接的に抑える                                                 |
| 従業員数       | 10人程度を想定 | 規模見積りであり、登録人数の上限ではない                                                                  |
| 出勤可能時間帯 | 1区間          | 未入力は当日休み                                                                                          |
| 休憩           | なし           | モデル外                                                                                                  |
| 店舗設定       | 設定画面なし   | 営業時間・役割名・コマ粒度はコード内の定数。役割は2種類を想定し、具体的な営業時間と役割名は実装時に決める |
| 外部出力       | なし           | 結果は画面表示だけ                                                                                        |
| 確定状態       | なし           | シフトの確定ワークフローは持たない                                                                        |
| 保存           | 自動保存       | 入力変更時と再求解時に保存。保存ボタンとundoは持たない                                                    |

30分コマ、1日計画、1日1勤務以下というモデル上の前提も初期版で固定する。

根拠: 決定事項 #4、#5、#15、#17、および依頼に列挙された「初期版の既定値」。

## 初期版で扱わない範囲を定める

- 人手で作ったシフトとの比較。
- ソルバーの制約を画面上で直接編集し、制約変更による再求解を見せる機能。通常の必要人数・出勤可能時間帯の編集と、ピン留め後の再求解は対象に含める。
- 従業員本人によるログイン、希望入力、閲覧、承認などの操作。
- 連勤上限、週の勤務時間の均しなどの日をまたぐ制約。
- 休憩の配置・管理。
- 時給を使った人件費計算。初期版の第2目的は総勤務時間で表す。
- 設定画面。営業時間、役割名、コマ粒度はコード内の定数として扱う。
- シフトの確定状態、印刷、CSVなどの外部出力。
- 認証・認可、アクセス制御。
- undo。

根拠: 決定事項 #1、#2、#4、#5、#8、#12、#14、#15、#17、および初期版の既定値。

### 技術上の要確認事項

依頼に記載された調査結果だけでは、次を採用確定の事実として扱わない。

- `highs@1.14.x` の正確なパッチ版、Workerからの呼び出し API、LP/MPS入力から解を読み戻す具体的な形式。`wasmModule` を渡す初期化経路がSvelteKitのWorkerビルドで動くかを確認する。
- `@sveltejs/adapter-cloudflare` のビルドで `.wasm` をバンドルする方法と、SvelteKit側の設定の細部。
- Workerスクリプトの gzip 後サイズ上限、CPU時間、メモリなどの現行値。調査では公式 Limits ページを取得できていないため、[公式 Limits ページ](https://developers.cloudflare.com/workers/platform/limits/)で再確認する。
- `highs@1.14.2` のファイルサイズは、調査時点で `build/highs.wasm` が3,078,627バイト、`build/highs.js` が68,966バイトという非圧縮値である。gzip後のサイズは未確認であり、[jsDelivrのパッケージAPI](https://data.jsdelivr.com/v1/package/npm/highs@1.14.2)の値だけでは採用可否を決めない。
- WorkerでのWASM読込に使うES module形式の扱いと、`highs` loaderの `wasmModule` 経路。前者の公式説明は[Cloudflare WebAssembly JavaScript API](https://developers.cloudflare.com/workers/runtime-apis/webassembly/javascript/)にあるが、本システムでの動作は未確認である。
- D1のマイグレーション、バインディング、SQLスキーマの物理設計、制限値、およびWranglerのバージョンに対応したコマンド。
- Svelteコンポーネントテストで使うDOM環境（jsdom等）とVitest設定。
- APIの具体的なルート、HTTPメソッド、リクエスト・レスポンス形式。要件上は従業員CRUD、日付データの読み書き、求解、初期化を提供することまでを確定する。

これらは作業計画の各検証ステップで確認し、確認できなかった場合は `yalps` への切り替えを含めて採用判断を更新する。
